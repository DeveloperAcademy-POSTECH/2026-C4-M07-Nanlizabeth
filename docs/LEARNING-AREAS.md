# 📚 회고 스터디 학습 영역 나누기 — "다 만든 코드로 뭘 공부할까"

> **이 문서는 뭔가요?** 이 프로젝트는 개발을 AI가 진행합니다. 그래서 "누가 무슨 기능을 만들지"를 사람에게 나눠주지 않습니다.
> 대신 **개발이 끝난 뒤**, 5명이 **이미 완성된 코드를 보고 회고하며 공부**할 때 **"각자 어느 부분을 깊게 팔지"**를 나눈 것입니다.
> 즉, 아래는 **개발 분담표가 아니라 학습 분담표**입니다.

> **문서 3형제와의 관계:** [SPEC.md](SPEC.md)(무엇을) · [ARCHITECTURE.md](ARCHITECTURE.md)(어떻게) · [ROADMAP.md](ROADMAP.md)(무슨 순서로) 를 **읽는 사람 기준으로 다시 자른 것**이 이 문서입니다.
> 기획자·초보 개발자도 읽을 수 있게 **쉬운 말**로 적었습니다.

## 0. 큰 그림 — 5명 = 5개 영역

기타 한 대를 두 기기로 나눠 든 앱이라, 공부할 덩어리도 자연스럽게 나뉩니다.

```
   [소리]        [통신]         [뼈대]          [연주 로직]       [손끝 = 접근성·햅틱]
  진짜 기타 소리를  아이폰↔아이패드를  앱이라는 건물의    "짚으면 소리 난다"를   소리·화면이 없어도
  만들어낸다      한 대로 잇는다     골조와 협업 방식    화면과 분리해 흐른다   진동으로 느끼게 한다
   1️⃣            2️⃣             3️⃣              4️⃣                5️⃣
```

> 💡 **왜 5개가 딱 맞나?** 원래 접근성은 "음성 명령 + 햅틱" 두 축이었는데, **음성 명령 기능을 빼기로 하면서** 접근성의 유일한 축이 햅틱이 됐습니다. 그래서 **"접근성·햅틱"이 5번째 영역으로 자연스럽게 자리 잡습니다.** 억지로 만든 5번이 아니라 원래 있어야 할 자리예요.

| # | 영역 | 한 줄 정의 | 난이도(공부 부담) |
|---|------|-----------|:---:|
| 1 | 소리 (오디오 엔진) | 명령을 진짜 기타 소리로 **만들어낸다(합성)** | 높음 |
| 2 | 통신 (멀티피어) | 아이폰(왼손)과 아이패드(오른손)를 무선으로 잇는다 | 중간 |
| 3 | 앱 전체 아키텍처 | 앱이라는 건물의 **골조 + 협업 방식** | 중간 |
| 4 | 비즈니스-UI 로직 아키텍처 | 연주 규칙을 **화면과 분리해** 흐르게 한다 | 높음 |
| 5 | 접근성 · 햅틱 | 소리·화면 없이 **손끝 진동**으로 느끼게 한다 | 중간 |

각 영역은 **① 한 줄 정의 → ② 뭘 공부하나 → ③ 볼 파일/문서(체크리스트) → ④ 얹으면 좋은 곁가지** 순서로 적혀 있습니다.

## 1️⃣ 소리 (오디오 엔진)

**한 줄:** "몇 번 줄을, 이 세기로 울려라"라는 명령을 받아 진짜 기타 소리를 **만들어내는(합성)** 부분. 녹음 파일을 트는 게 아닙니다.

**뭘 공부하나**
- `AVAudioEngine`(배선판) + `AVAudioUnitSampler`(악기) + `SoundFont(.sf2)`(음색 재료)가 어떻게 연결돼 소리가 나는지
- **스트럼의 정체** — 결국 "6현을 몇 ms 시차로 순차 발음"하는 것. 다운/업 = 발음 순서, 세게 긁음 = velocity(세기)
- 악기 앱이라 반드시 챙겨야 하는 것들:
  - **지연(latency)** — 터치→소리가 즉각이어야 함 (**악기 앱의 1순위 지표**, 발열·메모리보다 위)
  - **중단·경로 변경 복구** — 전화·알람·이어폰 꽂고 뺌·블루투스 전환 시 소리가 조용히 죽지 않게
  - **폴리포니 상한** — 6현+잔향이 겹쳐 음이 폭증할 때의 처리
- **Native vs AudioKit 두 엔진을 계약 뒤에 살려두고 나중에 고르는 A/B 전략** — 왜 지금 안 고르나

**볼 것 (체크리스트)**
- [ ] `GuitarSync/Domain/Audio/` 전체 (`GuitarAudioEngineProtocol` / `Base` / `Native` / `AudioKit` / `Factory`)
- [ ] `docs/tech-notes/audio-pipeline.md` (동작 원리)
- [ ] `docs/adr/0002-audio-engine.md` (왜 이 기술)
- [ ] ARCHITECTURE §3.1 (계약 + ⚠️ 지연·중단·폴리포니 보강 노트)

**🔧 얹으면 좋은 곁가지 — 성능 계측**
- `thermalState`(발열)·CPU·**터치→소리 지연**을 자동 기록해서 **엔진을 데이터로 고르는 도구**(ROADMAP A2). "어느 엔진이 더 나은가"를 감이 아니라 숫자로 판정하는 방법.

## 2️⃣ 통신 (멀티피어)

**한 줄:** 아이폰(왼손·코드)과 아이패드(오른손·스트로크)를 무선으로 이어 **한 대의 기타처럼** 만드는 부분.

**뭘 공부하나**
- `MultipeerConnectivity`로 근처 기기를 **찾고 → 초대하고 → 데이터를 주고받는** 흐름
- **핵심 설계 결정:** "스트럼 → 소리" 경로에는 **네트워크를 안 끼운다.** 아이폰은 "지금 코드가 뭔지"만 계속 보내고, 아이패드가 긁는 순간 **로컬에 저장된 코드로 즉시** 소리 냄 → 네트워크 지연이 스트럼 타이밍을 망치지 않음
- 메시지를 압축·복원하는 **코덱**
- **역할 고정** — iPad=항상 오른손, iPhone=항상 왼손 (협상 없음)
- **연결 상태 머신** — `idle → guide(첫 회만) → browsing → inviting → connected → disconnected`
- 첫 연결 때 뜨는 **로컬 네트워크 권한 팝업**(시스템이 띄움, 못 없앰 → 안내로 대응)

**볼 것 (체크리스트)**
- [ ] `GuitarSync/Services/Multipeer/` (`MultipeerService` / `Protocol` / `MessageCodec`)
- [ ] `GuitarSync/Models/PeerMessage.swift`, `PeerConnectionState.swift`
- [ ] `docs/adr/0001-multipeer-connectivity.md`
- [ ] ARCHITECTURE §3.8, SPEC 플로우 3

**🔧 얹으면 좋은 곁가지 — 원격 소스 & 끊김 처리**
- 수신 메시지를 `RemoteFingeringSource`/`RemoteStrumSource`로 포장해서 **코디네이터(4번 영역)는 원격인지도 모르게** 만드는 방식 (§3.7·§3.8이 만나는 지점 → 4번 담당과 대화하면 좋음)
- **연결이 끊겼을 때** 어떻게 할지(일시정지? 단독 모드 전환?)는 아직 열린 결정 (SPEC §8)

## 3️⃣ 앱 전체 아키텍처 (뼈대)

**한 줄:** 앱이라는 건물의 **골조** — 폴더 규칙, 화면 이동, 그리고 **"껍데기(계약)+가짜(Mock)"로 여럿이 동시에 개발하는 협업 방식.**

**뭘 공부하나**
- **폴더를 왜 이렇게 나누나** — Domain(화면 없이 도는 규칙) / Features(화면) / Services(기기·시스템 연동) / Content(데이터) / DesignSystem(색·여백)
- **라우터** — 화면 이동을 **한 곳에서** 관리하는 안내데스크. "그 화면 어떻게 여는 거예요?"를 없앰
- ⭐ **이 프로젝트의 핵심 협업 철학** — 계약(프로토콜)을 먼저 정하고 각자 그 껍데기만 보고 동시에 개발. **계약을 만들 때 Mock(가짜 대역)도 같이** 만들어서, 상대가 완성되기 전에 내 것을 개발
- **팩토리 + 런타임 교체** — 재빌드 없이 엔진을 즉시 바꾸는 A/B 토글

## 4️⃣ 비즈니스-UI 로직 아키텍처 (연주가 흐르는 방식)

**한 줄:** "짚으면 소리 난다 / 리듬대로 자동으로 긁는다" 같은 **규칙(로직)을 화면과 분리해** 만들고, **이벤트로** 화면과 연결하는 방식.

**뭘 공부하나**
- ⭐ **소스 + 코디네이터 "멀티탭" 구조 (§3.7 — 이 앱의 심장)**
  - 왼손 플러그(직접/자동/원격) × 오른손 플러그(직접/자동/원격)를 **갈아끼우기만** 하면 모드 A·B·C가 만들어짐
  - 모드를 `if`문 덩어리로 안 만들고 **플러그 조합**으로 만드는 이유
- ⭐ **이벤트 기반 UI 분리 (§3.4)** — UI는 "여기 눌렸어요(`FretPress`)"만 넘기고, 로직은 "3번 줄 울렸어요(`notePlayed`)"만 방송. **서로의 속사정을 모름** → 따로 개발 가능
- **박자 클럭에 플레이어들이 구독**해서 같은 박자로 도는 구조 (자동 스트럼·자동 진행·미리듣기가 전부 하나의 심장에 맞춤)

- [ ] `GuitarSync/Features/Strum/GuitarStrumViewModel.swift` (좌표→줄 매핑, 긁는 속도→세기)
- [ ] SPEC §2(왼손×오른손 조합표) · §4(개별 발음 요구사항)

**🔧 얹으면 좋은 곁가지 (두 개)**
- **박자·타이밍 정확도** — `BeatClock`을 `Timer`로 만들면 밀립니다(드리프트). `DispatchSourceTimer`·시작시각 기준 절대 계산, 더 촘촘하면 오디오 엔진 자체 클럭(샘플 단위 스케줄링)까지. "음악이 안 틀리게 하는 타이머"라는 깊은 주제 (§3.2)
- **데이터 & 저장** — 커스텀 진행/주법을 `Codable`로 JSON 저장, `UserDefaults`로 온보딩·연결 플래그 관리 (SPEC §7). **코드 부담이 적어 초보자가 붙기 좋은** 소재

## 5️⃣ 접근성 · 햅틱 (손끝이 두 번째 귀) ← 새로 추가

**한 줄:** 소리가 안 들리거나 화면을 못 봐도 **손끝 진동**으로 연주를 느끼고 **실수를 알아채게** 하는 부분. 음성 명령을 뺀 지금, **접근성의 핵심**입니다.

**이번에 정한 햅틱 두 가지, 그리고 왜 좋은 학습 주제인가**

| 햅틱 | 하는 일 | 왜 공부거리인가 |
|------|--------|----------------|
| **잘못된 코드 → 강한 진동** | 틀린 운지를 짚으면 강한 햅틱으로 "아니야!" 안내 | 단순 진동이 아니라 **"지금 짚은 운지(§3.4) vs 목표 코드(§3.3 카탈로그)를 비교하는 판정 로직"** 이 필요 → **접근성이 비즈니스 로직과 만나는 지점** |
| **현 튕김 → 강→약 서서히 감쇠** | 튕긴 순간 강하게, 실제 기타 줄이 잦아들 듯 서서히 약해지는 진동 | 지금 코드로는 **불가능** → 진짜 학습 포인트 (아래) |

**⚠️ 핵심 — 지금 `HapticsManager`로는 감쇠 진동을 못 만듭니다**
- 현재 `Services/Haptics/HapticsManager.swift`는 `UIImpactFeedbackGenerator`만 씁니다 → **딱 한 번 "툭"** 치는 것만 가능. 강→약으로 **서서히 변하는 곡선**을 못 그림
- "서서히 잦아드는" 진동을 만들려면 **Core Haptics(`CHHapticEngine`)** 로 올라가야 합니다:
  - **연속 이벤트(`CHHapticEvent .continuous`)** + **강도 감쇠 곡선(`CHHapticParameterCurve`, intensity)** 으로 실제 줄이 울리다 잦아드는 걸 흉내
  - 이게 **오디오의 "음이 감쇠한다"와 1:1로 짝**을 이룸 → 소리(1번)와 나란히 놓고 보면 이해가 확 됨
- 즉 이 영역의 학습 = **`UIImpactFeedbackGenerator` → Core Haptics로 발전시키기.**

**주의점 (문서에 이미 있음)**
- **iPad는 햅틱 하드웨어가 없음** → 모드 C(긁는 기기=iPad)에서 진동을 못 줌. 기기별 대체 피드백(시각?) 설계가 학습 포인트 (SPEC §5.2 · §8 열린 결정)
- 발음 햅틱은 **줄 애니메이션과 똑같은 이벤트(`notePlayed`)** 를 구독 → **화면 피드백과 짝으로** 봐야 함 (ARCHITECTURE §3.11, ROADMAP H1)

**볼 것 (체크리스트)**
- [ ] `GuitarSync/Services/Haptics/HapticsManager.swift` (현재 상태 → 발전 방향 비교)
- [ ] ARCHITECTURE §3.11(손맛·햅틱), SPEC §5.2(햅틱)
- [ ] Apple 공식 문서: **Core Haptics**, `CHHapticEngine`, `CHHapticEvent`, `CHHapticParameterCurve`
- [ ] (연계) §3.4의 `notePlayed` 이벤트 — 어디서 진동을 트리거받는지

**🔧 얹으면 좋은 곁가지 — 접근성 전반**
- 이 영역이 한 사람 몫으로 가볍다 싶으면 **VoiceOver 라벨 · 다이내믹 타입(글자 크기) · 모션 줄이기** 같은 iOS 접근성 전반으로 넓히기. "장애가 있어도 쓸 수 있는 앱"이라는 관점 자체가 좋은 공부.

## 6. 곁가지 한눈에 (놓치기 쉬운 것 모음)

앞에서 각 영역에 얹은 "곁가지"만 따로 모았습니다. **꼭 5명 밖으로 뺄 필요는 없고**, 관심 있는 사람이 자기 영역에서 파고들면 됩니다.

| 곁가지 주제 | 뭘 배우나 | 어느 영역에 얹나 |
|------------|----------|----------------|
| 성능 계측 | 발열·CPU·지연을 숫자로 재서 엔진 고르기 | 1️⃣ 소리 |
| 원격 소스 & 끊김 처리 | 원격을 소스로 포장, 연결 끊김 UX | 2️⃣ 통신 (+4️⃣) |
| 디자인 시스템/토큰 | 색·여백에 이름 붙여 일관성 지키기 | 3️⃣ 뼈대 |
| 박자·타이밍 정확도 | 안 밀리는 음악 타이머 만들기 | 4️⃣ 로직 |
| 데이터 & 저장 | Codable·JSON·UserDefaults | 4️⃣ 로직 (초보 추천) |
| 접근성 전반 | VoiceOver·다이내믹 타입·모션 줄이기 | 5️⃣ 접근성 |

## 7. 대안 — 분량이 안 맞을 때

**만약 "접근성·햅틱"이 한 사람 몫으로 가볍다면** → **햅틱 + SwiftUI 애니메이션·제스처**를 묶어 **"손맛(햅틱 + 시각 피드백)"** 영역으로 만들 수 있습니다.

- 근거: 둘 다 **`notePlayed`라는 똑같은 이벤트를 구독**하는 짝이라, 문서상으로도 함께 설계하게 돼 있습니다 (ARCHITECTURE §3.11, ROADMAP H1·U3).
- 이러면 5번이 "**손끝(햅틱)과 눈(줄 떨림 애니메이션)으로 연주를 느끼게 하는 피드백 전문가**"가 되어 무게가 실립니다.

반대로 **소리(1번)나 로직(4번)이 너무 무겁다** 싶으면, 곁가지(성능 계측 / 타이밍 정확도)를 떼어내 별도 담당에게 주는 것도 방법입니다.

## 8. 정리 — 이 문서 한 줄

> 개발은 AI가, **회고 학습은 5명이** — **소리 · 통신 · 뼈대 · 연주 로직 · 접근성(햅틱)** 다섯으로 나눠, 각자 "볼 파일 체크리스트"만 따라가면 됩니다. 음성 명령이 빠진 자리에 **햅틱이 접근성의 주인공**으로 들어섭니다.
