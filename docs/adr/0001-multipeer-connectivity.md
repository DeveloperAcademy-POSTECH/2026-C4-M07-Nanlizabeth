# ADR 0001: 기기 간 통신에 MultipeerConnectivity 채택

## 상태
채택됨 (Accepted)

## 맥락

GuitarSync는 아이폰(왼손/코드)과 아이패드(오른손/스트로크)를 한 대의 기타처럼 연동해야 한다. 두 기기가 실시간으로 상태를 주고받되, 다음 조건을 만족해야 했다.

- 별도 서버나 인터넷 없이 두 기기가 직접 연결될 것
- 설정이 복잡하지 않고, 사용자가 앱만 켜면 근처 기기를 찾을 것
- 코드 상태 전송의 지연이 낮을 것

## 고려한 선택지

1. **MultipeerConnectivity** — 애플이 제공하는 근거리 P2P 프레임워크. Wi-Fi/블루투스를 자동으로 활용하고, 기기 탐색·연결·데이터 전송을 한 API로 처리.
2. **Network.framework (직접 소켓 구현)** — 더 낮은 레벨에서 TCP/UDP를 직접 제어. 유연하지만 기기 탐색(Bonjour)·연결 관리를 전부 직접 구현해야 함.
3. **중앙 서버 경유 (WebSocket 등)** — 두 기기가 서버를 통해 통신. 인터넷 의존적이고 지연이 크며, 오프라인에서 동작 불가.

## 결정

**MultipeerConnectivity를 채택한다.**

근거리 두 기기 연결이라는 우리 시나리오에 정확히 맞고, 기기 탐색부터 연결까지를 표준 API로 처리해주어 개발 범위를 크게 줄여준다. 인터넷 없이 동작하므로 "앱만 켜면 바로 연주" 경험에 부합한다.

## 결과

**장점**
- 서버 인프라 불필요, 오프라인 동작 가능
- 기기 탐색·연결·재연결 로직을 프레임워크가 상당 부분 처리

**감수하는 단점 / 유의점**
- iOS 14+부터 `NSLocalNetworkUsageDescription`과 `NSBonjourServices` 선언이 필수이며, 누락 시 **에러 없이 조용히 탐색이 실패**함
- 전송 신뢰도(`.reliable`) 모드는 head-of-line 블로킹으로 지연이 커질 수 있어, 최신값만 유효한 코드 상태 전송에는 `.unreliable` 사용을 검토
- 통신 지연이 존재하므로, 소리 발생 경로를 네트워크에 의존시키지 않는 설계가 필요 → ADR 0002 참고
