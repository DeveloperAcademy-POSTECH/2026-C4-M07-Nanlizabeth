# ADR 0003: 두 오디오 엔진을 계약 뒤에 두고 최종 선택을 미룬다

## 상태
채택됨 (Accepted) · **[ADR 0002](0002-audio-engine.md)를 확장한다** (대체가 아니라 보강)

## 맥락

[ADR 0002](0002-audio-engine.md)에서 네이티브 `AVAudioEngine`을 채택했다. 그런데 개발을 진행하며 두 가지가 분명해졌다.

- **AudioKit이 실제로 더 나을 수도 있다.** AudioKit도 결국 내부는 `AVAudioEngine`이지만, 샘플러·믹서 구성이 더 간결하다. 어느 쪽이 **지연·메모리·발열**에서 유리한지는 **감이 아니라 실기기 데이터**로만 알 수 있다.
- **지금 하나로 못 박으면 되돌리기 비싸다.** 엔진을 코드 곳곳에서 직접 부르면 나중에 바꿀 때 전 코드를 손대야 한다.

즉 "어떤 엔진이 최선인가"라는 질문의 **답을 지금 낼 근거가 없고**, 근거는 개발이 끝나갈수록(데이터가 쌓일수록) 좋아진다.

## 고려한 선택지

1. **ADR 0002대로 네이티브 하나만 쓰고 끝낸다.** 단순하지만, AudioKit이 더 나았을 가능성을 영영 확인 못 한다. 나중에 바꾸려면 전면 수정.
2. **AudioKit 하나로 갈아탄다.** 반대 방향의 같은 도박 — 네이티브가 더 나았을 가능성을 못 본다.
3. **둘 다 `GuitarAudioEngineProtocol` 뒤에 살려두고, 런타임에 교체 가능하게 한 뒤, 최종 선택은 출시 직전으로 미룬다.**

## 결정

**선택지 3 — 두 엔진을 계약(`GuitarAudioEngineProtocol`) 뒤에 두고, 최종 선택을 출시 직전으로 미룬다.**

- 공통 로직(음 계산·벨로시티·자동 정지)은 `GuitarAudioEngineBase`에 모으고(Template Method), 실제 소리 내는 부분만 `NativeAudioEngine` / `AudioKitAudioEngine`이 오버라이드한다.
- 엔진 선택 분기(`#if canImport(AudioKit)`, `USE_AUDIOKIT`)는 `GuitarAudioEngineFactory` 한 곳에만 둔다. 나머지 코드는 전부 프로토콜에만 의존한다.
- 디버그 빌드의 **런타임 A/B 토글**(`DebugAudioEngineToggle`)로 재빌드 없이 두 엔진을 즉시 바꿔가며 같은 조건에서 비교한다.
- **최종 결정은 데이터가 가장 많이 쌓인 출시 직전**(ROADMAP 태스크 I5)에 지연·메모리·발열을 종합해 내린다. 진 쪽 파일은 그때 정리한다.

## 결과

**장점**
- "어느 엔진이 나은가"를 **데이터가 가장 많을 때** 판정 → 가장 정확한 시점에 결정
- 지금 안 정해도 **다른 개발이 하나도 안 막힌다** — 모두 계약에만 기대므로
- AudioKit 패키지가 없는 환경에서도 컴파일되게 `#if canImport(AudioKit)`로 가드 → 의존성 유무와 무관하게 빌드 성공

**감수하는 단점 / 유의점**
- 엔진이 두 벌 유지되므로 **버그·개선을 양쪽에 반영**해야 한다 (공통은 `Base`로 최대한 모아 완화)
- 두 엔진을 동시에 인스턴스화하면 **샘플러·사운드폰트가 2배** 로드돼 메모리를 낭비한다. 그래서 **한 번에 한 엔진만** 살아 있어야 하고, 성능 계측(A3)은 이 점을 감안해야 한다
- 최종 정리(I5) 전까지는 "우리 엔진은 무엇" 이라고 단정할 수 없다 — 문서·발표에서 이 잠정성을 분명히 밝힌다

## 관련
- 되살리기 어렵지 않게 계약 뒤에 둔다는 발상은 [ADR 0001](0001-multipeer-connectivity.md)의 "소리 경로를 네트워크에 의존시키지 않는다"와 같은 철학(교체 가능성 확보)이다.
- 계측 도구로 데이터를 쌓는 방법 → ROADMAP A2·A3, `docs/LEARNING-AREAS.md` 1️⃣.
