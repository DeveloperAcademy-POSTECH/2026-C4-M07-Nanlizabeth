# ADR 0004: 모드를 "소스 플러그 조합"으로 만든다 (소스·코디네이터)

## 상태
채택됨 (Accepted)

## 맥락

GuitarSync는 연주 모드가 여럿이고, 앞으로 더 늘 수 있다.

| 모드 | 왼손(운지) | 오른손(스트로크) |
|------|-----------|-----------------|
| A. 코드 연습 | 🖐️ 직접(넥) | 🤖 자동(주법) |
| B. 스트로크 연습 | 🤖 자동(진행) | 🖐️ 직접(긁기) |
| C. 합주 | 📡 원격(iPhone이 짚음) | 🖐️ 직접(iPad가 긁음) |

이걸 순진하게 짜면 **`if mode == .A { … } else if mode == .B { … }`** 식 분기가 소리·화면·입력 곳곳에 퍼진다. 모드가 하나 늘 때마다 여러 파일의 `if`를 동시에 고쳐야 하고, 조합이 꼬이기 쉽다.

핵심 관찰: **모든 모드는 "왼손을 어떻게 채우나 × 오른손을 어떻게 채우나"의 조합일 뿐**이다. 왼손·오른손 각각이 **직접 / 자동 / 원격** 세 방식 중 하나다.

## 고려한 선택지

1. **모드별 분기(`if`/`switch`)를 각 소비자에 둔다.** 직관적이지만 모드가 늘수록 분기가 사방에 번지고, "이 모드에서 소리는 어디서 나지?"를 추적하기 어렵다.
2. **모드마다 전용 클래스(ModeAController, ModeBController…)를 따로 만든다.** 분기는 사라지지만 모드 간 중복이 크고(다들 "긁으면 그 순간 운지로 소리"), 새 조합마다 클래스를 통째로 새로 짠다.
3. **왼손·오른손을 각각 "플러그(소스)"로 추상화하고, 코디네이터가 둘을 꽂아 소리로 만든다.** 모드 = 플러그 조합.

## 결정

**선택지 3 — 소스 + 코디네이터 "멀티탭" 구조.** (ARCHITECTURE §3.7)

- **왼손 플러그** `FingeringSourceProtocol` — "지금 무슨 코드를 짚나"를 공급. 구현 3종: `ManualFingeringSource`(넥 터치) · `AutoFingeringSource`(코드진행 플레이어) · `RemoteFingeringSource`(피어 수신).
- **오른손 플러그** `StrumSourceProtocol` — "언제 어떻게 긁었나"를 방송. 구현 3종: `ManualStrumSource` · `AutoStrumSource`(주법 플레이어) · `RemoteStrumSource`.
- **코디네이터** `PlaySessionCoordinator` — 하는 일은 하나: **오른손이 긁는 순간, 그 순간의 왼손 운지를 읽어 오디오를 호출한다.** 왼손이 사람인지 자동인지 원격인지는 **알지도 못하고 알 필요도 없다.**
- 모드 조립체는 그 조합을 묶은 것뿐이다: `ChordPracticeSession`(Manual×Auto) · `StrumPracticeSession`(Auto×Manual) · `EnsembleStrummerSession`(Remote×Manual).

```
왼손 플러그 ─┐
             ├─▶ Coordinator ──▶ AudioEngine
오른손 플러그 ─┘   (긁는 순간의 운지로 소리)
```

## 결과

**장점**
- **모드 추가 = `if`문이 아니라 플러그 조합 하나 추가.** 코디네이터·소스는 그대로. 이게 이 결정의 핵심 이득이다.
- **원격이 투명하다.** 통신(N1)이 수신 운지를 `RemoteFingeringSource`에 넣으면, 코디네이터는 원격인지도 모른 채 동작한다. 모드 C가 "왼손 플러그만 원격으로 바뀐 모드 B"로 성립한다.
- **테스트가 쉽다.** 소스에 Mock을 꽂아 소리 경로를 화면·네트워크 없이 검증할 수 있다(기록형 가짜 엔진 + `MockBeatClock`).
- 이벤트 분리(§3.4: UI는 `FretPress`만 넘기고 로직은 `notePlayed`만 방송)와 짝을 이뤄, 로직과 화면이 서로의 속사정을 모른 채 동시에 개발된다.

**감수하는 단점 / 유의점**
- 처음 보면 "왜 이렇게 겹겹인가" 싶은 **간접 계층**이 있다 — 소스·코디네이터·세션. 익숙해지기 전엔 흐름 추적에 품이 든다.
- 코디네이터가 "긁는 순간의 운지"를 읽는 타이밍이 핵심이라, 소스들이 **같은 스레드(MainActor)에서 일관되게** 갱신돼야 한다.

## 관련
- 자동 왼손/오른손을 미는 플레이어(코드진행·주법)는 하나의 **박자 클럭**(`BeatClock`)에 구독한다 → 타이밍 결정은 별개 주제(ARCHITECTURE §3.2).
- 이 구조를 학습 관점으로 푼 설명 → `docs/LEARNING-AREAS.md` 4️⃣.
