# ADR 0002: 오디오 합성 엔진으로 AVAudioEngine 채택

## 상태
채택됨 (Accepted) · **확장됨 — [ADR 0003](0003-dual-audio-engine-behind-contract.md) 참고.**
개발 중 AudioKit을 대안으로 함께 `GuitarAudioEngineProtocol` 뒤에 두고, 네이티브 vs AudioKit **최종 선택을 출시 직전으로 미루기로** 했다. 이 문서(0002)는 "네이티브를 왜 골랐나"의 근거로 유효하며, "왜 하나로 안 박고 둘 다 살려두나"는 0003이 이어 받는다.

## 맥락

Chordly의 핵심 경험은 "긁으면 즉시 기타 소리가 난다"이다. 이를 위해 다음이 필요했다.

- 6현을 개별적으로 제어(스트럼의 시차·방향·강약 표현)
- 코드에 맞는 음을 실시간 합성
- 스트로크 입력과 소리 사이의 지연 최소화

또한 통신 지연(ADR 0001)이 소리 타이밍을 망치지 않도록, **오디오 엔진은 스트로크를 담당하는 아이패드(연주 기기)에 두는 것**을 전제로 한다.

## 고려한 선택지

1. **미리 녹음된 코드 사운드 재생 (AVAudioPlayer)** — 코드별 오디오 파일을 재생. 구현은 가장 단순하나, 스트럼의 현별 시차·방향·세기를 표현할 수 없어 "진짜 기타 같은" 느낌이 나지 않음.
2. **AVAudioEngine + AVAudioUnitSampler** — 애플 네이티브 저수준 오디오 엔진. SoundFont(sf2)를 로드해 현별로 음을 트리거하고, 노드 그래프로 시차·볼륨·이펙트를 정밀 제어 가능.
3. **AudioKit (서드파티 라이브러리)** — AVAudioEngine을 감싼 고수준 추상화. 신스·샘플러 구현이 편하고 개발 속도가 빠르나, 외부 의존성이 추가되고 세밀한 제어 시 결국 하부를 이해해야 함.

## 결정

**AVAudioEngine + AVAudioUnitSampler를 채택한다.**

스트럼의 현별 시차·방향·강약이라는 우리 앱의 핵심 표현을 구현하려면 현 단위의 정밀 제어가 필수적이다. 외부 의존성 없이 애플 생태계 안에서 저지연으로 처리할 수 있고, 학습 측면에서도 오디오 파이프라인을 직접 이해하게 되는 이점이 있다.

> 개발 속도가 병목이 될 경우 AudioKit 도입을 재검토할 수 있으나, 초기에는 네이티브로 진행한다.

## 결과

**장점**
- 6현 개별 제어로 스트럼의 시차·방향·세기 표현 가능
- 외부 의존성 없음, 저지연
- `AVAudioSession`을 `.playback` 카테고리로 설정해 무음 스위치와 무관하게 소리 출력

**감수하는 단점 / 유의점**
- AVAudioPlayer 방식보다 초기 구현 난도가 높음(SoundFont 준비, 보이스 관리, 폴리포니 처리)
- 오디오 렌더 스레드에서 메모리 할당·락을 피해야 하는 등 실시간 오디오 주의사항 학습 필요
- 저지연을 위해 `setPreferredIOBufferDuration`을 낮추면 CPU 부담과 트레이드오프
