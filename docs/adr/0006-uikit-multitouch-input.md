# ADR 0006: 기타 입력은 UIKit 멀티터치로 받는다 (SwiftUI 제스처 아님)

## 상태
채택됨 (Accepted)

## 맥락

기타는 본질적으로 **여러 손가락이 동시에** 닿는 악기다.

- **기타넥(왼손)** — 화음은 여러 칸을 여러 손가락으로 동시에 짚는다 (SPEC §4 개별 발음).
- **스트럼(오른손)** — 아르페지오처럼 여러 손가락이 각자 다른 줄을 동시에 튕길 수 있다.

화면은 SwiftUI로 짜므로, 처음엔 터치도 SwiftUI 제스처(`DragGesture`)로 받았다.

## 문제 (실기기에서 드러남)

**SwiftUI `DragGesture`는 손가락을 하나만 준다.** 세 손가락으로 C코드를 짚어도 하나만 들어오고, 여러 줄을 동시에 튕겨도 한 줄만 울렸다. 화음·아르페지오라는 기타의 기본 동작이 안 됐다.

## 고려한 선택지

1. **SwiftUI 멀티 제스처 조합**으로 우회. 제스처를 여러 개 붙여도 SwiftUI는 동시 터치를 낱개 좌표로 안정적으로 주지 않는다. 실전에서 꼬임.
2. **`UIViewRepresentable` + `isMultipleTouchEnabled` UIView**로 내려가 `touchesBegan/Moved/Ended/Cancelled`를 직접 받는다.
3. **SpriteKit/Metal 등 별도 렌더 레이어**로 입력을 받는다. 과하다.

## 결정

**선택지 2 — 멀티터치는 UIKit `UIView`로 받아 SwiftUI에 올린다.** (`DesignSystem/Components/MultiTouchLayer.swift`)

- `isMultipleTouchEnabled` 뷰가 **"지금 닿아 있는 손가락 전부"를 스냅샷으로** 올려보낸다. began/ended를 낱개로 올리면 손가락이 빠르게 엇갈릴 때 상태가 어긋나므로, **매 이벤트마다 "지금은 이게 전부다"**를 통째로 넘긴다.
- **좌표를 의미로 바꾸는 일(어느 줄·어느 프렛)은 레이어가 아니라 화면 쪽**에서 한다(`NeckGeometry`, 스트럼 좌표 계산). 레이어는 "손가락이 어디에 닿아 있다"까지만 안다.
- 넥·스트럼이 **같은 `MultiTouchLayer` 하나**를 공유한다.
- `UITouch` 객체는 이벤트 처리 밖에서 붙잡지 않고 **식별자·좌표만 복사**해 들고 있는다(Apple 규약).

> 스트럼의 "긁기"는 손가락 하나로 쓸어내리는 동작이라 `DragGesture`로도 됐지만, 아르페지오(동시 튕김)를 위해 스트럼도 같은 멀티터치 레이어로 통일했다.

## 결과

**장점**
- 화음(동시 짚기)·아르페지오(동시 튕김)가 실제로 된다 — 기타 앱의 필수 동작.
- 스냅샷 방식이라 손가락이 엇갈려도 상태가 어긋나지 않는다.
- 입력 레이어(UIKit)와 좌표 해석(화면)이 분리돼, 화면마다 좌표 규칙만 다르게 얹으면 된다.

**감수하는 단점 / 유의점**
- **시뮬레이터로는 검증이 안 된다.** 마우스는 손가락 하나뿐이고 Option 조합은 핀치라, 임의의 동시 터치를 만들 수 없다 → 멀티터치는 **실기기 검증 항목**.
- UIKit↔SwiftUI 경계를 하나 두는 비용이 있으나, 레이어 한 파일로 국한된다.
